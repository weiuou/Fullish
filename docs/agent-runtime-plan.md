# Dim agent 与 visualize 插件开发路径

2026-11-12 修订：用户确定直接由 Dim 绘图。当前合同见 [Issue #48](https://github.com/weiuou/Fullish/issues/48)，实现与发布证据见 [接入指南](agent-runtime.md)。原沙箱方案已[归档](archive/2026-11-12-agent-sandbox-plan.md)，不再指导新绘图功能。

## 架构与职责

Fullish 接收 QQ 消息、选择群上下文并建立受限 Dim 任务。Dim 自己规划与调用 rutis 的 visualize 插件；插件执行本地渲染并把 PNG 返回模型检查。Fullish 仅授权绘图票据、接收本轮图片与最终候选，再通过共享发送入口获得 QQ 确认。

保持模块化单体和专用同机 companion。通用沙箱仍是独立可选工具；绘图不进入 broker，不要求群沙箱权限。不能把模板或指南的存在当作已经接入真实渲染。

## 接入合同与恢复

每次绘图只把格式、尺寸、源码字节数交给 Fullish 授权；源码留在插件。票据只接受一次完成，PNG 绑定本轮媒体库，候选登记不是 QQ 回执。总任务 90 秒、单次绘图 25 秒、最多两次绘图；模型循环与桥接调用另有上限。撤权后禁止提交和投递。

固定错误码帮助模型进行一次修正，但格式或资源失败仍可能发生；直接执行不等于保证所有绘图成功。取消时撤销授权并停止浏览器，无法确认的执行记为不明。已受理任务不自动改用旧后端重跑；QQ 不明回执不补发。

迁移需协调 companion、bot、Compose 和 `DIM_VISUALIZATION`，先暂停新绘图并排空任务。保留旧镜像、配置与最小运行登记，按实际状态回退，不删除私有卷。部署检查使用插件固定本地管理探针，不调用付费模型或 QQ。

## 验证方式与完成定义

先做合成场景：真实内部输入、授权、Dim/插件、浏览器、媒体与发送服务，只模拟外部模型与 QQ；断言图片真的进入模型输入、最终字节一致且确认后才记历史。再在实际 Linux 镜像检查资源、取消、私有 RPC 与无 broker 执行。CI 通过后，受控真实模型和 QQ 的验收独立记录；长期质量、容量和费用需单群观察。

持续会话、公开网页和后台执行均需先在 Issue 中明确接口、存储、保留、预算及恢复方式，不隐含在本次直接渲染中。
