# 架构与部署决策

## 当前边界

当前实现是一个 NoneBot2 + FastAPI 驱动的基础进程，通过 `/health/live`、`/health/ready` 和 `/version` 验证构建、启动、更新及版本追溯。它不连接 QQ、不调用模型，也不保存聊天数据。健康响应的 `mode=foundation` 和 `qq_connected=false` 明确表达这一点。

采用单仓库、模块化单体。初期一台腾讯云服务器运行一个 Fullish 实例；优先建立可靠的发布方式，再增加会话能力。

## 运行与发布分离

GitHub 托管运行器处理代码检查、测试和镜像构建，镜像存入 GHCR 或配置的仓库。受信任的 `main` 工作流调用腾讯云自动化助手 TAT，由服务器执行预先安装的部署脚本。

此方案适合当前的单机 Ubuntu / Debian 环境：服务器保留运行配置和部署状态，GitHub 保留代码、检查结果与构建记录，镜像 digest 将一次部署精确对应到一次构建。服务器无需拉取源码或安装开发依赖。

| 信息 | 保存位置 |
| --- | --- |
| 源代码、工作流、锁文件、配置模板 | GitHub 仓库 |
| 构建镜像、提交号、digest | 镜像仓库与 Actions 运行记录 |
| TAT 命令 ID、实例 ID、地域 | GitHub `production` 环境变量 |
| 调用 TAT 的专用 CAM 凭证 | GitHub `production` 环境 Secrets |
| QQ / 模型等应用密钥 | 服务器 `/opt/fullish/runtime.env`，在接入时添加 |
| 已部署与上一个成功镜像 | 服务器部署状态文件 |

生产服务器不运行可执行外部 PR 的 GitHub runner。TAT 调用执行保存的命令，不需要为 GitHub Actions 放开服务器 SSH 入站。TAT 密钥仍具有部署权限，按生产凭证管理。

## 发布的一致性

部署输入使用 `仓库路径@sha256:摘要`，而非可能被覆盖的标签。脚本先获取镜像，再替换容器并等待健康检查；成功后记录版本，失败时尝试恢复上一镜像并将本次部署标记为失败。

GitHub 部署并发控制与服务器进程锁共同限制并行更新。Compose 保持单个机器人实例，避免未来 QQ 接入时新旧实例同时发言。单机替换可能有短暂停机，当前不承诺无中断部署。

容器以非 root 用户运行，健康端口只绑定服务器回环地址，配置与应用镜像分开，日志使用轮转策略。需要公网 QQ Webhook 时，再按适配器要求配置域名、HTTPS 和入口转发；基础阶段不暴露健康服务到公网。

## 后续模块

| 模块 | 后续职责 |
| --- | --- |
| `adapters` | 群消息入口、私聊过滤、QQ 事件转换 |
| `conversation` | 按群排队、话题上下文、发言决定、过期结果丢弃 |
| `providers` | 可替换模型、超时、调用成本 |
| `memory` | 带群作用域和来源的记忆更新、检索与删除 |
| `personas` | 版本化人格和示例对话 |
| `evals` | 合成或脱敏群聊回放、自然度和发言时机评测 |

同一个群同时最多生成一条候选回复；发送前重新检查消息时效、群预算与会话状态。接入 QQ 后，要将连接、消费消息和发送队列等必要条件纳入 readiness；模型短暂不可用是否应使服务不就绪，需要按故障恢复策略单独决定。

## 数据持久化后的变化

需要长期记忆时再引入 PostgreSQL、SQLAlchemy 和 Alembic。数据库与应用镜像有不同的恢复方式：回滚应用镜像不会恢复被修改的数据。

数据库上线前必须确定备份位置、恢复演练、保留期及兼容迁移约定。优先采用新增字段等向后兼容的迁移，让上一镜像仍可运行；删除字段等破坏性变更分阶段完成。不要把自动降级数据库作为镜像回滚的一部分。

## 扩展顺序

先在现有服务器验证发布、重启恢复和回滚，再接入 QQ 与模型。随着贡献者和群数增长，添加独立测试群、受控集成评测和测试环境；只有实际负载需要时才拆分队列、数据库或增加实例。当前无需引入 Kubernetes 或额外服务器。
